# Plan — deno-runtime

## Objective

Every TypeScript project in the monorepo runs and tests on **Deno**, used purely as a runtime;
nothing depends on Bun, OpenTUI, or the current Solid/Vite front ends. `Deno.*` is usable freely
and type-checked by `tsgo` against Deno's own declarations, generated by Nx into `node_modules`.
pnpm owns resolution, Nx owns tasks, there is no `deno.json`. `pnpm run check` and the Nx `test`
targets are green.
This is the precursor to kuib's own terminal UI library (see D005) — the old UI is removed
rather than ported, so the new library starts from an empty `host-tui` view layer.

## Non-goals

- Building the new TUI library (follow-up feature; D005 records its direction).
- Replacing pnpm or Nx — the repo also holds non-TS projects (`services/stt-coreml`,
  `services/stt-mlx`) that Nx orchestrates.
- Deno-specific tooling: no `deno.json`, no `deno check`, no `denols` (D006).
- Replacing eslint/prettier with `deno lint`/`deno fmt` (house-style rules are eslint plugins).
- Distribution (`deno compile` binaries) — follows once a host has a UI again.
- Porting host-web; it is removed, not migrated.

## Principles

1. Startup cost is a feature: no FFI/`dlopen` on the start path, no runtime transpile hooks,
   no sloppy module resolution probes.
2. Prefer built-in Deno / `node:` APIs over npm packages where they are faster or native.
3. Deletions are real deletions — no dead flags, stubs, or commented-out UI.
4. Mechanical migrations land as mechanical diffs (import swaps), separate from behavioral ones.

## Decisions

### D001 — Deno is the runtime and test runner; pnpm + Nx stay

- Status: superseded
- Context: Bun was chosen only because OpenTUI's native renderer needs FFI. With OpenTUI
  gone, the user wants off Bun and onto Deno, using Deno APIs where they speed things up.
  The monorepo also contains Swift/Python services orchestrated by Nx.
- Options considered: full Deno toolchain (Deno workspaces, `deno lint`/`fmt`, drop
  pnpm/Nx); Deno runtime only with pnpm + Nx kept; stay on Bun.
- Decision: Deno runs and tests all TS code. pnpm remains the package manager, Nx the task
  runner/cache, eslint/prettier the lint/format tools.
- Consequences: Deno must resolve pnpm workspace packages from source (G002); two
  manifests per root (`package.json` + `deno.json`). Non-TS projects are unaffected.
- Supersedes: —
- Superseded by: D006

### D002 — Remove OpenTUI by deletion, not porting

- Status: accepted
- Context: kuib will own its whole UI stack (D005). The existing UI surface is small (~840
  lines host-tui, ~1000 lines wireframes, a Vite/Solid host-web) and built on OpenTUI
  components and `@opentui/keymap`.
- Options considered: stub the TUI to plain stdout; keep the code excluded from checks;
  delete the view layer and the UI-only apps.
- Decision: delete `apps/wireframes`, `apps/host-web`, and host-tui's view layer. Keep
  host-tui's non-UI plumbing (`cli`, `run/serve`, `log`, `resolve.daemon.client`).
- Consequences: no interactive UI until the new library lands; `pnpm wireframes` and the
  design-session picker go away (wireframe markdown stays as UX truth). The host-web
  concurrent-turn gap noted in host-layer becomes moot.
- Supersedes: —
- Superseded by: —

### D003 — Built-in `node:sqlite` over FFI sqlite

- Status: accepted
- Context: `bun:sqlite` must be replaced. The user measured `dlopen` hurting startup.
- Options considered: `jsr:@db/sqlite` (FFI, loads a native lib); `npm:better-sqlite3`
  (N-API addon); `node:sqlite` (built into Deno and Node).
- Decision: `node:sqlite` `DatabaseSync`.
- Consequences: no native library load on startup; code stays runtime-portable between
  Deno and Node. API differences from `bun:sqlite` need a pass (G003).
- Supersedes: —
- Superseded by: —

### D004 — Explicit import extensions instead of sloppy imports

- Status: accepted
- Context: the codebase uses extensionless relative imports (`./log`), which Deno only
  accepts with sloppy-imports resolution — extra filesystem probes per import at startup.
- Options considered: enable `sloppy-imports`; rewrite specifiers to explicit `.ts`
  paths (`allowImportingTsExtensions` is already on).
- Decision: rewrite to explicit paths via codemod.
- Consequences: one large mechanical diff; resolution is exact and cheapest.
- Supersedes: —
- Superseded by: —

### D005 — Direction for the follow-up TUI library

- Status: accepted
- Context: recorded here so the removal is not mistaken for abandoning a UI. The user wants
  full control over rendering and look, peak performance, and fast startup; `dlopen`-based
  native cores hurt startup.
- Options considered: keep OpenTUI's core and own components; own everything including
  reactivity; own everything below Solid.
- Decision: pure TypeScript, owned end to end below the reactive layer — terminal I/O and
  input parsing, cell buffer + diff, grapheme width, an owned flex subset (no Yoga),
  components, keymap. Solid stays as the reactive core via `solid-js/universal`
  `createRenderer`; frame scheduling is owned by the renderer, not by Solid effects.
- Consequences: Solid JSX needs a compile step on Deno (G005) — paid at build time for
  shipped binaries. The renderer depends only on the universal-renderer contract, so Solid
  stays replaceable.
- Supersedes: —
- Superseded by: —

### D006 — Deno as a pure runtime; tsgo type-checks against generated Deno types

- Status: accepted
- Context: D001 assumed a root `deno.json` and Deno-side type-checking. Exploring that
  (2026-09-22, Deno 2.9.7) showed every Deno-specific tool fights the pnpm workspace:
  Deno ignores `pnpm-workspace.yaml`, needs its own copy of the catalog, `deno add`
  overwrites `catalog:` entries, and a root-level resolution error makes Deno rewrite the
  root `package.json` with the workspace + catalog. The user wants `Deno.*` usable freely
  without changing tooling.
- Options considered: root `deno.json` + `deno check` + `denols`; drop pnpm for Deno
  workspaces/catalogs; restrict code to `node:` APIs (no `Deno.*`); keep `tsgo` and feed it
  Deno's own declarations from `deno types`; `@types/deno` (2.7.0, lags the runtime, lacks
  web globals).
- Decision: no `deno.json`. pnpm resolves, Nx runs tasks, Deno only executes
  (`deno run`/`deno test` with `--no-check`). `tsgo` is the single type-checker, in CI and
  the editor. Deno's types come from `deno types`, generated by an Nx target into the
  `@kuib-ai/deno-types` workspace package (gitignored output, linked into `node_modules`),
  referenced from `base.json` `types` next to `node`.
- Consequences: verified in isolation — `tsc` 6.0.3 and `tsgo` 7 both pass `Deno.*` +
  `node:*` + web globals, and catch real errors; Deno/Node global declaration clashes stay
  inside `.d.ts` files and require `skipLibCheck: true` (already set). Deno resolves pnpm's
  symlinked `@kuib-ai/*` packages from source without configuration. Import specifiers
  must be explicit (D004) since sloppy imports would need a flag on every command. Deno
  commands must run per project (P02-I06). The editor keeps `tsgo`; `denols` never starts
  in kuib (no Deno root marker).
- Supersedes: D001
- Superseded by: —

## Gaps

### G001 — How TS typechecks Deno globals

- Status: resolved
- Context: `tsc --noEmit` does not know `Deno.*`. Options: generate `deno types` into a
  checked-in `.d.ts` included by `@kuib-ai/tsconfig`, or switch `typecheck` targets to
  `deno check`. Decide in P02-I04.

### G002 — Deno resolution of pnpm workspace packages

- Status: resolved
- Context: pnpm symlinks workspace packages into `node_modules`, and Deno refuses TypeScript
  inside npm packages. Workspace members must be resolved via `deno.json` `workspace`
  instead. Verify with the installed Deno version before the codemods. Resolved: Deno 2.9.7
  follows pnpm's symlinks to the real `packages/*` paths and loads the TypeScript from
  source with no config; types-only `exports` still fail at runtime (P02-I03).

### G003 — `node:sqlite` parity with `bun:sqlite` usage

- Status: open
- Context: `db.run`, `db.query().all()`, transactions, and binding style differ. Audit
  `event-log-sqlite` call sites before swapping. Research (2026-09-22): Deno's `node:sqlite`
  is rusqlite compiled into the binary (no `dlopen`); ~2x slower than Node on insert loops
  and slower than `bun:sqlite` per call, irrelevant for an fsync-bound event log. Porting:
  `DatabaseSync`, `readOnly`, `prepare()` instead of `query()`, manual `BEGIN IMMEDIATE`;
  Deno ≥ 2.9.7 rejects symlinked DB paths.

### G004 — Deno not installed on this machine

- Status: resolved
- Context: Homebrew here is owned by another user; install via the official script
  (`~/.deno`) or a Homebrew-owning account. Resolved: Deno 2.9.7 installed to
  `~/.deno/bin` via the official script (shell PATH left to the user).

### G005 — Solid JSX compile pipeline on Deno

- Status: open
- Context: follow-up feature concern. Deno's built-in JSX transform cannot run

### G006 — Pinning the Deno version across machines

- Status: resolved
- Context: Bun was provisioned by pnpm (catalog-pinned, `node_modules/.bin`), so every mesh
  node ran the same runtime with no system install. Deno is currently a per-machine install
  (`~/.deno/bin`, 2.9.7) that each developer must put on `PATH`; nothing pins its version.
  `@kuib-ai/deno-types` keys its cache on `deno --version`, so drift regenerates types
  rather than breaking silently. Options not yet evaluated: a pnpm-provisioned Deno
  binary, or a version check in `check`.
  Resolved (2026-09-22): `deno` is a root devDependency, catalog-pinned to `2.9.6` (the
  newest on npm; GitHub's 2.9.7 is not yet published there) with `allowBuilds: deno: true`,
  so `pnpm install` provisions it into `node_modules/.bin` like Bun was. pnpm and Nx
  scripts resolve it from there; the journal hooks call `./node_modules/.bin/deno`.
  Verified green with no global `deno` on `PATH`. Cost: the `.bin` shim starts Node to
  launch the binary (~40 ms per dev command vs ~10 ms direct); kuib's runtime startup is
  unaffected.
