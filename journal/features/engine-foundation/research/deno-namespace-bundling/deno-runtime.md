# Deno-first single-executable packaging and deferred initialization

Part of [[features/engine-foundation/research/deno-namespace-bundling]].

Research date: **2026-10-06**. Target runtime supplied by coordinator: **Deno 2.9.6**, whose release page is dated **2026-08-27** ([release](https://github.com/denoland/deno/releases/tag/v2.9.6)). Discovery used the configured `firecrawl search --sources web --no-domain-tools`; substantive pages were fetched with `firecrawl scrape`. Raw JSON, including source metadata, is in `sources/deno/`; searches returning no results have command records. No application changes or new performance experiments were performed.

**Bottom line:** one executable does not require one eagerly evaluated JavaScript module. Plain compilation supports embedded literal dynamic imports. Even a single esbuild bundle can preserve deferred initialization; that does not mean its source bytes or parsing costs disappear. Namespace spelling and evaluation timing are separate design choices. [Deno compile documentation](https://docs.deno.com/runtime/reference/cli/compile/); [esbuild semantics](https://esbuild.github.io/api/#splitting)

## 1. What evaluates at startup, and what do dynamic imports, bundling and namespaces change?

### Takeaway

Ordinary runtime static imports bring their dependency initialization onto the startup path, whether imported as named bindings or namespaces. Literal dynamic imports provide an asynchronous evaluation boundary inside one executable; Deno 2.8+ also offers experimental synchronous-on-access deferred namespaces. [MDN static import](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import); [Deno modules](https://docs.deno.com/runtime/fundamentals/modules/)

### Cited Findings

- **Ordinary static imports:** MDN says their side effects occur “before the rest of the module's code runs.” This concerns the runtime import graph, including transitive dependencies, not every file in the repository. `import * as Protocol` does not itself make evaluation lazy. The namespace is a view of exports, not an initialization policy. **Language documentation, last modified 2026-09-11 and 2026-09-15.** [Static import](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import#hoisting); [namespace objects](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object)
- **Literal dynamic import in plain `deno compile`:** docs explicitly say statically analyzable dynamic imports, with “the string literal within the `import("...")` call expression,” are included in the output. Their example says `calculator.ts` **and its dependencies** are included. Inclusion at build time is distinct from evaluation at runtime: Deno's module guide presents conditional `await import("./greet.ts")` specifically to keep rarely used features off the startup path. **Official docs, compile updated 2026-08-06; modules updated 2026-06-30.** [Compile](https://docs.deno.com/runtime/reference/cli/compile/); [modules](https://docs.deno.com/runtime/fundamentals/modules/)
- **`compile --bundle` in precisely 2.9.6:** the tagged `bundle_for_compile` implementation sets `format: BundleFormat::Esm`, `code_splitting: false`, `inline_imports: true`, `packages: PackageHandling::Bundle`, and `platform: BundlePlatform::Deno`; `minify` is passed independently. Thus the main entry is bundled into one JS output, rather than using esbuild's dynamic-import chunk splitting. This is implementation evidence pinned to the target release, not an inference from today's help text. [2.9.6 source](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/tools/bundle/mod.rs)
- **One JS bundle can still delay initialization:** esbuild documents that without splitting, an `import()` becomes `Promise.resolve().then(() => require())`: “This still preserves the asynchronous semantics” while placing imported code in the same bundle. This supports deferred execution of dynamic-only module initialization even with a single output. It does **not** promise deferred loading/parsing of that whole output or deferred dependencies also reached statically. **Upstream bundler documentation; no publication/update date displayed, retrieved 2026-10-06.** [esbuild splitting](https://esbuild.github.io/api/#splitting)
- **`--minify` is separate:** Deno documents it as meaningful with `--bundle`, reducing embedded size and runtime memory at the cost of stack-trace readability. Maintainer Bartek Iwańczuk's PR describes adapting the dynamic-`require` shim to minified variable names. Neither source says minification turns dynamic initialization eager or guarantees a particular startup/RAM saving. **PR opened 2026-05-29, merged 2026-06-02; shipped in the 2.9 release announced 2026-06-25.** [PR #34536](https://github.com/denoland/deno/pull/34536); [compile docs](https://docs.deno.com/runtime/reference/cli/compile/#minifying-the-bundle); [2.9 announcement](https://deno.com/blog/v2.9#deno-compile)
- **Important namespace-shaped candidate: `import defer * as Protocol`:** Deno explicitly supports deferred module evaluation starting in **2.8**. Its docs say the module and dependencies load, but the module's top-level code waits until the first namespace property read. The announcement also documents `import.defer()` and says modules can be “loaded and parsed without running [their] top-level code.” This fits a synchronous-on-access namespace direction, but is **experimental Stage 3 syntax**, not a finalized language guarantee. **Announcement 2026-05-22; implementation PR merged 2026-04-29.** [Module guide](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation); [2.8 announcement](https://deno.com/blog/v2.8#import-defer); [PR #32360](https://github.com/denoland/deno/pull/32360)
- **Deferred-import caveat:** the implementation PR explicitly handles asynchronous transitive dependencies before resolving dynamic `import.defer()`. Do not generalize the simple synchronous example into “no dependency can run before any property read.” [PR #32360, `evaluate_for_import_defer` change](https://github.com/denoland/deno/pull/32360/commits/5502a81b5d93dff85ca50a35560a9241b4924bd2)
- **Loading is not evaluation:** the unstable-flags docs separately describe `--unstable-lazy-dynamic-imports` as delaying loading of statically analyzable imports when type checking is off. The modules guide's broad statement that dynamic imports are only fetched when invoked must therefore not be read as a universal guarantee about build-time fetching or eager graph preparation. The stable conclusion is the runtime evaluation boundary. **Flags docs updated 2026-07-02.** [Unstable flags](https://docs.deno.com/runtime/reference/cli/unstable_flags/#--unstable-lazy-dynamic-imports); [module guide](https://docs.deno.com/runtime/fundamentals/modules/)

### Inferences

- **`Protocol.Message.User` can be preserved as an API shape without choosing eager initialization.** An asynchronously acquired module can expose that nested shape after its load boundary; an experimental deferred namespace offers synchronous property access with first-access evaluation. An ordinary static namespace barrel remains eager. These are planning alternatives, not a recommendation to change the API. [Dynamic namespace result](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import); [Deno deferred namespace](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation)
- Reading `Protocol.Message` through a deferred `Protocol` namespace triggers evaluation at the **Protocol module boundary**; it does not automatically confer an independent lazy boundary on every deeper property such as `User`. A barrel that statically re-exports many expensive implementations can therefore activate a broader graph than intended. Namespace organization and deferred-module granularity need to be considered together. [Deferred property-access semantics](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation); [static side-effect semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import#hoisting)
- To preserve a dynamic-only startup boundary, its heavy dependency must not also be reached by an ordinary eager import elsewhere. Minification/tree-shaking may remove unreachable code, but retained side-effectful initialization is different from unused declarations. [esbuild linking/tree-shaking architecture](https://github.com/evanw/esbuild/blob/main/docs/architecture.md#tree-shaking)

### Gaps

- No retrieved Deno test/documentation explicitly certifies **`import defer` + `deno compile --bundle --minify`** together on 2.9.6. Runtime support is documented; parser/transpiler/bundler interoperability for this combination remains a separate question. Do not present it as a verified drop-in choice.
- No application-specific evidence establishes which Kuib namespace modules allocate costly objects, start services, load native code, or are duplicated on eager and deferred paths. This research deliberately did not audit or change application source.

## 2. Does one executable require one bundle, and what limits inclusion and pnpm/native compatibility?

### Takeaway

The executable is a packaging boundary, not necessarily a JavaScript module boundary. Plain compilation embeds a module graph; bundled compilation can additionally contain worker bundles, explicit included files and native/npm packages. The target's pnpm/BYONM path needs special attention because its package-pruning behavior differs from managed npm. [Compile docs](https://docs.deno.com/runtime/reference/cli/compile/); [2.9.6 writer](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/standalone/binary.rs)

### Cited Findings

- **Default embedding:** compile docs describe an executable containing the program and dependencies, with embedded files served by a virtual filesystem. `--bundle` is an **optional, experimental** pre-bundling stage. Consequently “one executable requires one eager JS bundle” is contradicted by the documented default path and dynamic-import support. [Compile documentation, updated 2026-08-06](https://docs.deno.com/runtime/reference/cli/compile/)
- **Computed imports:** `import(specifier)` with a runtime-computed path is not automatically discoverable, even if the variable chooses between two filenames. Docs instruct using `--include <path>` for the missing modules. Included `.js`/`.ts` files become module-graph roots and are resolved/transpiled. `--include-as-is`, introduced in **2.9**, embeds bytes without module resolution/transpilation and is intended for assets/prebuilt files. It is not equivalent to resolving a TypeScript module's dependency graph. [Compile documentation](https://docs.deno.com/runtime/reference/cli/compile/); [2.9 release](https://deno.com/blog/v2.9#deno-compile)
- **Bundled dynamic-pattern limits:** docs say nonliteral dynamic `require()`/`import()` patterns cannot be traced; use statically analyzable patterns, explicit inclusions, or plain compilation. This is a packaging limitation, not proof that literal `import()` is eagerly evaluated. [Compile limitations](https://docs.deno.com/runtime/reference/cli/compile/#limitations)
- **Workers and chunks:** plain compile requires explicitly including undiscovered worker roots. Bundled compile recognizes `new Worker(new URL("./worker.ts", import.meta.url), ...)`, bundles workers separately, and embeds them alongside the main bundle. Computed worker URLs and workers spawned from transitive dependencies remain documented limits. Standalone **`deno bundle --code-splitting --outdir ...`** is separately documented; **`compile --bundle` has splitting disabled in 2.9.6**. [Compile workers/bundling](https://docs.deno.com/runtime/reference/cli/compile/); [bundle docs, updated 2026-06-24](https://docs.deno.com/runtime/reference/cli/bundle/); [tagged bundler source](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/tools/bundle/mod.rs)
- **Native/CJS support is present, with qualifications:** current docs describe detecting CJS and `.node` addons and embedding supporting packages. The first bundle PR's unsupported-native/CJS limitations were followed by fixes; do not quote that first-cut description as today's blanket restriction. Native-addon packages are externalized so their relative `.node` loading keeps its original directory context. **Initial PR merged 2026-05-31; native/CJS fix merged 2026-06-01.** [PR #34527](https://github.com/denoland/deno/pull/34527); [PR #34529](https://github.com/denoland/deno/pull/34529); [2.9.6 bundler source](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/tools/bundle/mod.rs)
- **pnpm/BYONM is the strongest concrete packaging caveat:** maintainer PR #34532 states, “BYONM keeps the prior whole-tree behavior,” because precise pruning needs workspace-layout awareness. The 2.9.6 source still returns no precise package set for BYONM, and the writer's corresponding bundled npm fallback calls `fill_npm_vfs`. Thus managed-npm reachability savings must not be assumed for externally installed pnpm trees when npm embedding is required. Pure-ESM bundles that avoid that fallback are a different case. **PR merged 2026-06-01; corroborated by target-tag source.** [PR #34532](https://github.com/denoland/deno/pull/34532); [2.9.6 native-addon/package collection](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/standalone/native_addons.rs); [2.9.6 writer](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/standalone/binary.rs)
- **Managed-only alternative exists:** `--exclude-unused-npm` is documented to embed reachable managed npm packages, with “no node_modules directory”; non-statically analyzable imports need explicit `--include npm:...`. Its scope is not the same as pruning an existing pnpm workspace. The condition is present in the 2.9.6 writer. [Flag docs](https://docs.deno.com/runtime/reference/cli/compile/#options-exclude-unused-npm); [2.9.6 writer](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/standalone/binary.rs)
- **Community pnpm report, not a proven 2.9.6 failure:** issue #30509 is **open in the retrieved page**, opened **2025-08-24**, tested on **2.4.3** and then-main commit `6314c3c`. It reports symlink-resolution failures for manual `node_modules` using pnpm's isolated linker; its proposed cause is explicitly the reporter's guess. An unanswered discussion dated **2025-03-18** separately reports an entire pnpm monorepo entering the executable. These justify an explicit compatibility question, not a claim that all pnpm compiles are currently broken. [Issue #30509](https://github.com/denoland/deno/issues/30509); [discussion #28536](https://github.com/denoland/deno/discussions/28536)
- **One distributed file need not imply no runtime disk materialization:** current docs offer `--self-extracting` for code/native addons needing real files. It extracts embedded files on first run, with extra first-start work and disk usage. The docs explicitly list higher memory usage because embedded content “can no longer be referenced as static data.” This is a distinct mode, not required for ordinary dynamic JS imports. [Self-extracting executable documentation](https://docs.deno.com/runtime/reference/cli/compile/#self-extracting-executables)
- **Historical closed issue:** #5562, opened **2020-05-17**, requests dynamic-import code splitting in the old bundle command and is now closed. Current `deno bundle` explicitly supports code splitting. The old request is historical motivation, not evidence of a current absence. The retrieved issue page did not expose its closing rationale or full comment history. [Issue #5562](https://github.com/denoland/deno/issues/5562); [current bundle docs](https://docs.deno.com/runtime/reference/cli/bundle/)

### Inferences

- **Pre-split modules could still ship in one executable:** compile a generated entry whose chunks remain literal module imports, including computed roots explicitly. This follows the documented graph inclusion model, but is a **candidate assembly approach**, not a verified Kuib build recipe. Plain `deno compile` already supplies a simpler module-preserving candidate; choosing either is pending the user's priorities. [Literal imports and inclusion](https://docs.deno.com/runtime/reference/cli/compile/); [Deno bundle splitting](https://docs.deno.com/runtime/reference/cli/bundle/)
- Native dependency handling and pnpm layout may dominate artifact size independently of namespace style or deferred initialization. A smaller JS bundle alone does not prove a smaller embedded npm tree on the BYONM path. [2.9.6 native-addon collection](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/standalone/native_addons.rs)

### Gaps

- Cross-target `.node` compatibility, ancillary shared libraries, package install scripts and this workspace's actual symlink graph were not verified. Current support for `.node` does not establish universal npm-native compatibility.
- The open pnpm issue does not establish whether its exact reproducer still fails in 2.9.6. No experiment was run.
- Generated split bundles can change module layout and ordering; esbuild itself documents a cross-chunk import-ordering issue. This remains a reason to review that candidate before adoption. [esbuild splitting caveat](https://esbuild.github.io/api/#splitting)

## 3. What is known about startup, memory, caching and unloading, and what plan follows?

### Takeaway

Evidence supports separating **artifact size**, **resident/mapped memory**, **V8 heap/external allocations**, and **initialization work**. Deferred initialization can avoid work and allocations for unused features, but neither deferred imports nor minification promises module unloading or a measured application-specific RAM/startup reduction. [Deno memory API](https://docs.deno.com/api/deno/~/Deno.memoryUsage); [deferred evaluation](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation); [module caching](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object)

### Cited Findings

| Quantity | What the evidence supports |
| --- | --- |
| Executable / embedded payload bytes | Maintainer PR #34532 reports lodash hello-world **11.62 MB → 1.45 MB embedded payload** and a native fixture **10.62 MB → 468 KB**. These are fixture payload measurements, **not full executable sizes, RAM measurements or Kuib forecasts**. The 2.9 blog's shorter “binaries” wording should be qualified by the PR's precise “embedded payload” wording. [PR, merged 2026-06-01](https://github.com/denoland/deno/pull/34532); [blog, 2026-06-25](https://deno.com/blog/v2.9#deno-compile) |
| Resident / mapped memory | `Deno.memoryUsage().rss` reports process bytes occupying RAM; `heapUsed` is a separate V8 metric. Compile docs distinguish static embedded data from the higher-memory self-extraction mode. Neither source establishes that every executable byte is resident, copied to the heap, or untouched until the matching import. Exact 2.9.6 demand-paging/mapping behavior remains unverified here. [Memory API, no displayed update date](https://docs.deno.com/api/deno/~/Deno.memoryUsage#Deno.MemoryUsage); [compile VFS/extraction](https://docs.deno.com/runtime/reference/cli/compile/#self-extracting-executables) |
| Heap objects / external allocations | Deno separately reports V8 `heapTotal`, `heapUsed`, and memory associated with JS objects outside the isolate as `external`. Delaying an initializer is distinct from removing its source from the artifact. [Memory API](https://docs.deno.com/api/deno/~/Deno.memoryUsage#Deno.MemoryUsage); [deferred evaluation](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation) |
| Startup initialization work | `import defer` explicitly permits loading/parsing without executing top-level code. Dynamic-import lowering can retain deferred execution inside one bundle. These support avoiding startup evaluation costs, **not** a guarantee that all parsing/module-record/runtime costs disappear. [Deno 2.8](https://deno.com/blog/v2.8#import-defer); [esbuild](https://esbuild.github.io/api/#splitting) |

- **Code cache is not initialized application state:** the **2.1 announcement, 2024-11-21**, introduced V8 code caching for compiled executables, describing a cache created on first run in a temporary directory for subsequent runs. It publishes a `hyperfine --warmup 2` comparison of **282.9 ± 6.5 ms versus 129.7 ± 6.8 ms**, calling the improvement workload-dependent. This is an old warm-run benchmark, not a 2.9.6 cold-start forecast. Current compile docs expose `--no-code-cache`, and the 2.9.6 writer generates a versioned cache key from graph sources when enabled. [2.1 announcement](https://deno.com/blog/v2.1); [current flag](https://docs.deno.com/runtime/reference/cli/compile/#options-no-code-cache); [2.9.6 writer](https://raw.githubusercontent.com/denoland/deno/v2.9.6/cli/standalone/binary.rs)
- **Maintainer startup evidence is runtime-wide:** the **2.9 announcement, 2026-06-25**, attributes startup gains to lazy Node globals, less eager Node bootstrap, caching residual lazy ESM and snapshot minification. It reports roughly **34 ms → 17 ms** hello-world cold start against 2.8 on dedicated x86_64 Linux, with a stated mean of 150 `hyperfine` runs. Its RSS figures concern HTTP server workloads at concurrency 100. Neither benchmark isolates `compile --bundle`, dynamic-import choices, namespace structure or this application. [2.9 performance section and linked implementation PRs](https://deno.com/blog/v2.9#performance)
- **No ordinary ESM unload API:** MDN says successful module imports are aggressively cached and “there is no way to manually clear the cache of module namespace objects.” Unique query strings can create additional module identities and cause memory growth, rather than unload the original. This supports budgeting module-associated retained state after first use. It does **not** mean every temporary object ever allocated by a module is immortal. **MDN updated 2026-09-15.** [Dynamic-import caching](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object)
- **Historical Deno cache issue:** #6946, opened **2020-08-03**, now closed, asks for reimport/cache deletion and worries that query-string variants retain both versions. The exposed body includes reporter speculation; the scrape did not expose maintainer comments/closing rationale. Use current language documentation for the conclusion, not the old issue as a current maintainer guarantee. [Issue #6946](https://github.com/denoland/deno/issues/6946)

### Inferences

- A useful low-RAM distinction is **never initialized**, **initialized but disposable resources explicitly released**, and **module still cached**. An import boundary can help with the first; it does not provide the second or an unloading mechanism. If eventually every heavy feature is used, initial savings need not translate to lower long-lived steady-state memory. [Deno deferred semantics](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation); [ESM cache semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object)
- Source-minification and code-cache benefits concern different costs from constructing schemas, registries, clients or native resources in module initialization. A benchmark must attribute those separately before concluding which packaging/API choice matters. [Minification docs](https://docs.deno.com/runtime/reference/cli/compile/#minifying-the-bundle); [code-cache announcement](https://deno.com/blog/v2.1); [deferred initialization](https://deno.com/blog/v2.8#import-defer)

#### Proposed plan for the coordinator to present, not implement

1. **Map the eager path:** identify expensive top-level initialization and runtime static/re-export paths behind the desired namespaces; identify genuinely optional feature boundaries.
2. **Ask the API question first:** must first `Protocol.Message.User` access be synchronous? Is an explicit asynchronous feature-load boundary acceptable? Is experimental `import defer` acceptable? These are owner choices; namespace spelling alone does not decide them.
3. **Keep packaging candidates explicit:** plain compile preserving modules; experimental compile bundling, with/without minification; and, only if useful, separately split output embedded into one executable. Review pnpm/BYONM and native-package inclusion before selecting a candidate.
4. **Define a future measurement matrix:** time to useful CLI/UI readiness; first optional-feature latency; cold versus warm code-cache runs; full artifact and embedded payload sizes; RSS and V8 heap/external values before and after first use and resource disposal. Include a target-machine relocation/offline compatibility check. Execute only in a later implementation/validation task after the user chooses a direction.

### Gaps

- No controlled 2.9.6 benchmark found comparing the same application under all of plain compile, bundled compile, minified compile and pre-split embedded modules. No defensible Kuib performance number follows from this research.
- Exact 2.9.6 embedded-byte mapping, page residency, transient copying, retained parser/code-cache memory and native-addon extraction paths were not traced end-to-end. The memory table deliberately avoids claiming zero RAM for uninvoked modules.
- The old code-cache announcement's precise on-disk placement/lifecycle was not independently reverified against 2.9.6 runtime loader code; target-tag evidence confirms cache-key generation, not every storage detail.
- Some GitHub issue scrapes exposed bodies/status but not full activity. Quoted PR discussions were available; absent issue comments were not reconstructed from search snippets.
