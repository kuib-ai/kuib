# Nested namespace APIs, esbuild tree-shaking, and deferred initialization in Deno

Part of [[features/engine-foundation/research/deno-namespace-bundling]].

Research date: **2026-10-06**. This is research for a decision, not an implementation or a selected design. All web discovery used the installed `firecrawl search`; all retrieved pages used `firecrawl scrape`. Raw search results and scrapes are in `sources/namespaces/` beside this file. GitHub HTML scrapes omitted comments, so the corresponding GitHub REST comment endpoints were also scraped; those raw files preserve authors, timestamps, full bodies, and permanent comment URLs. Documentation without a publication date is identified below as live documentation accessed on the research date.

## 1. Can `Protocol.Message.User` remain while unused members are pruned?

### Takeaway

**The spelling is compatible with tree-shaking in principle, but the current recursively imported default-object implementation does not provide that guarantee, and changing it only to nested ESM namespace reexports does not resolve esbuild's documented limitation.** The strongest evidence is esbuild maintainer Evan Wallace's explicit distinction between one-level namespace tracking and reexported namespaces, supported by a separate explanation of ordinary-object pruning hazards. [Maintainer on namespace tracking](https://github.com/evanw/esbuild/issues/1420#issuecomment-873786196); [maintainer on objects](https://github.com/evanw/esbuild/issues/2855#issuecomment-1398604378).

### Cited Findings

- **Direct maintainer confirmation, 2021-07-05:** Evan Wallace: “Tree shaking is supported with `import * as x` but not when `x` is then re-exported and re-imported. Imports are only tracked through one level, not through multiple levels.” Issue #1420's example uses `export * as constants`, then `constants.X`, but retains `Y`. Its scraped page remains **open**, labeled `suboptimal-output`; the original report does not identify an esbuild version. **Confidence: high for the historical implementation and stated limitation; current applicability supported, but not proven universally, by the supplied Deno probes.** [Issue #1420](https://github.com/evanw/esbuild/issues/1420); [maintainer comment](https://github.com/evanw/esbuild/issues/1420#issuecomment-873786196).

- **Architecture explanation, 2022-10-28:** Wallace says namespace-property “devirtualization” is “currently only one level deep.” Parsing creates special import-reference nodes/symbols; linking merges those symbols without another full AST traversal; substitution occurs at print time. Longer chains could potentially be represented, but entail additional complexity. This is an implementation trade-off, not a language prohibition or an announcement that the feature can never be implemented. The preceding community reproduction explicitly used **esbuild 0.15.12**. **Confidence: high.** [Maintainer explanation, #2636](https://github.com/evanw/esbuild/issues/2636#issuecomment-1295405909); [versioned reproduction](https://github.com/evanw/esbuild/issues/2636#issuecomment-1292915785).

- **Do not conflate `export *` and `export * as`:** A community clarification dated 2021-11-04 shows ordinary `export * from './constants.js'` followed by a named import/export can be shaken; exporting the namespace itself as a named binding is the problematic case. The current esbuild documentation independently demonstrates a flat `import * as lib` with `lib.one()` eliminating `two()`. **Confidence: high for the documented flat case.** [Clarification](https://github.com/evanw/esbuild/issues/1420#issuecomment-961323828); [esbuild tree-shaking docs, live](https://esbuild.github.io/api/#tree-shaking).

- **Plain objects are a separate problem, 2023-01-20:** Issue #2855 requests almost exactly the project's pattern: import `foo`, `bar`, `baz`, construct `const Lib = { foo, bar, baz }`, and default-export it. Wallace responds that `lib.foo()` gives `foo` the entire object through `this`, which can access the other members; deleting them can be incorrect. On 2024-06-10 he explicitly says the nested-ESM proposal is “a completely separate feature” and points back to #1420. The scraped #2855 page is still open. **Confidence: high.** [Issue #2855](https://github.com/evanw/esbuild/issues/2855); [2023 maintainer comment](https://github.com/evanw/esbuild/issues/2855#issuecomment-1398604378); [2024 distinction](https://github.com/evanw/esbuild/issues/2855#issuecomment-2157062060).

- **The `this` distinction has an intentional esbuild qualification:** Its current documentation says calls through an actual ESM namespace may be rewritten to direct calls, losing the namespace `this` context. That documented optimization exception does not turn a user-created default-export object into an ESM namespace. **Confidence: high.** [esbuild content types: namespace `this`, live](https://esbuild.github.io/content-types/#module-namespace-this).

- **Whole-namespace use changes the problem:** A 2023-06-19 community comment supplies esbuild **0.18.4** examples showing `console.log(Functions)` materializing a namespace containing both exports, and compares direct member access with escaping the namespace. It is a community proposal, not an implemented esbuild flag. **Confidence: medium as historical examples; high that its proposed opt-in flag must not be presented as existing functionality.** [Detailed community examples](https://github.com/evanw/esbuild/issues/1420#issuecomment-1596336911).

- **Library versus application entry point:** esbuild documents entry-point exports as part of the output module interface. Rollup makes this distinction explicit: `preserveEntrySignatures: 'strict'` keeps the original entry exports and is recommended for libraries; `false` can omit entry exports and their unused code for application entry points. **Confidence: high.** [esbuild output formats, live](https://esbuild.github.io/api/#format); [Rollup entry signatures, live](https://rollupjs.org/configuration-options/#preserveentrysignatures).

- **Other bundlers establish possibility, not a replacement decision:** The original #1420 report gives a Rollup output that removes the unused nested namespace member. Wallace says the analogous advanced optimization was added in **Webpack 5**, not Webpack 4. In #2636, TypeScript contributor Jake Bailey reported that Rollup emitted better code for his namespace case but that he encountered execution-order problems in that particular conversion. These are dated reports, not claims about every current build. **Confidence: high for what the sources report; medium for transfer to other inputs.** [Original Rollup comparison, 2021-07-04](https://github.com/evanw/esbuild/issues/1420); [Webpack version qualification, 2021-07-05](https://github.com/evanw/esbuild/issues/1420#issuecomment-873786196); [TypeScript conversion trade-off, 2022-10-28](https://github.com/evanw/esbuild/issues/2636#issuecomment-1295418965).

### Inferences

- **For the supplied current code, two independent barriers apply:** reachable aggregate objects keep their members referenced, and schema-construction calls can remain effectful even after an export becomes unused. Switching object barrels to ESM may address the first barrier for a more capable bundler, but nested namespace reexports still encounter esbuild's separate tracking limitation. **Confidence: high, conditional on the code description supplied in the assignment.** [Object discussion](https://github.com/evanw/esbuild/issues/2855#issuecomment-1398604378); [namespace discussion](https://github.com/evanw/esbuild/issues/1420#issuecomment-873786196); [conservative effect analysis](https://esbuild.github.io/api/#tree-shaking-and-side-effects).

- **Static access is favorable, not sufficient:** `Protocol.Message.User` exposes a concrete path, but esbuild must understand that full path to prune its siblings. An unknown runtime key, enumeration, or passing the namespace to opaque code can make all exports observable. Object spreading reads all enumerable properties at that point; whether later optimization can eliminate portions of a local spread depends on escape/use analysis. A computed key that is actually constant need not have the same outcome as an unknown runtime key. Do not state that every bracket access or spread always disables every optimization. **Confidence: high as semantic reasoning, unmeasured for this project.** [Namespace-object semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object); [esbuild namespace escape examples](https://github.com/evanw/esbuild/issues/1420#issuecomment-1596336911); [esbuild analysis architecture](https://github.com/evanw/esbuild/issues/2636#issuecomment-1295405909).

- **An exported library root is not evidence of an application-level failure:** If the bundle exposes the whole `Protocol` object as public output, retaining its members preserves the API for unknown consumers. A closed application entry point that actually consumes only `Protocol.Message.User` offers different reachability evidence. This is why a benchmark must identify its entry point and exported output contract. **Confidence: high.** [esbuild formats](https://esbuild.github.io/api/#format); [Rollup entry signatures](https://rollupjs.org/configuration-options/#preserveentrysignatures).

- **Preserving syntax is a feasible design constraint, not a claim that the existing build already satisfies it:** nested ESM namespaces processed directly by a capable bundler are one documented route; source-level rewriting or a separately designed lazy facade would be different contracts to assess. A first bundler that has already converted module bindings into ordinary runtime objects may remove information useful to a later optimizer; direct-source Rollup evidence does not establish that Rollup can repair every esbuild output. **Confidence: medium for multi-stage implications.** [Rollup comparison](https://github.com/evanw/esbuild/issues/1420); [esbuild lowering explanation](https://github.com/evanw/esbuild/issues/2636#issuecomment-1295405909).

### Gaps

- The assignment supplies these **local observations, not rerun in this research**: Deno **2.9.6**, with and without `--minify`, retained an unused function for recursive plain objects and for nested ESM namespace reexports; a flat namespace import removed it. Rollup **4.64.0** directly on nested ESM sources removed it, while the current object pattern retained it. Those are consistent with the sources above, not a complete benchmark or proof about all bundlers.
- Exact esbuild version used by the project's Deno 2.9.6 invocation, flags exposed by that Deno command, final executable entry point, escaped/enumerated namespaces, and the current code's use of getters, `this`, mutation, and cycles were not independently audited.
- Open issue state is useful corroboration, not proof that every release or every subcase behaves identically. The maintainer architectural explanations are explicitly dated 2021–2024.

## 2. Can modules stay embedded in one executable but remain uninitialized?

### Takeaway

**Yes, deferred evaluation is a different goal from removing bytes, and current sources identify a particularly relevant Deno-native option: Deno 2.8 added `import defer`, which retains synchronous namespace property access.** It requires explicit evaluation boundaries and does not make an ordinary eager barrel lazy; a Deno **2.9.5** report says non-bundled compilation works while bundling fails, so the exact Deno/esbuild pipeline remains decisive. [Deno 2.8 announcement](https://deno.com/blog/v2.8#import-defer); [Deno #36560, 2026-08-12](https://github.com/denoland/deno/issues/36560).

### Cited Findings

- **Ordinary ESM is eager:** MDN says ordinary static imports are hoisted and their side effects occur before the importing module's remaining code runs. Namespace import syntax is not a lazy per-property loader. A native namespace exposes live bindings, whereas the supplied object initializer constructs a normal object containing the imported values. **Confidence: high.** [MDN import hoisting, live](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import#hoisting); [MDN namespace objects, live](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object).

- **Dynamic import defers loading/evaluation until called and is asynchronous:** `import()` fulfills with the namespace after successful evaluation. Deno's compile documentation says string-literal dynamic imports are included in the executable by default; computed specifiers need explicit inclusion where they cannot be statically traced. This separates binary inclusion from runtime evaluation. **Confidence: high.** [MDN dynamic import, live](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import); [Deno compile dynamic imports, live](https://docs.deno.com/runtime/reference/cli/compile/#dynamic-imports).

- **Native synchronous deferral is no longer merely hypothetical:** Deno's **2026-05-22 / Deno 2.8** announcement says “Deno now supports the TC39 import defer proposal.” It demonstrates `import defer * as deferred` with the module's top-level log appearing only when `deferred.value` is read, and also documents `import.defer()`. Current Deno fundamentals likewise say this starts in **2.8**. **Confidence: high for documented runtime support.** [Deno 2.8 announcement](https://deno.com/blog/v2.8#import-defer); [Deno deferred module evaluation](https://docs.deno.com/runtime/fundamentals/modules/#deferred-module-evaluation).

- **Deferral is module-granular, not export-granular:** MDN's `import defer` page, last modified **2026-09-22**, says property access executes “the module's top-level code, not just the code needed to initialize the requested export.” Dependencies with their own deferred imports can remain deferred. Ordinary imports of the same module defeat deferral; top-level-await modules and dependencies needed for their asynchronous evaluation are eager. Fetching/parsing/linking still happen up front. **Confidence: high for documented semantics.** [MDN import defer description](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#description); [caching](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#caching_semantics); [top-level await](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#top-level_await).

- **Reexporting a deferred namespace need not initialize it:** MDN documents that there is no `export defer` syntax, but importing a deferred namespace and exporting its binding does not trigger evaluation. Passing/storing the namespace alone also need not trigger evaluation; reading its string properties, destructuring them, or enumerating keys does. Only namespace import syntax is supported for static `import defer`, not default or named forms. **Confidence: high.** [Exporting deferred namespace](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#exporting_a_deferred_namespace); [evaluation triggers](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#deferred_module_namespace_object).

- **Recent direct compiled-executable evidence, with limitations:** Deno issue **#36560**, opened **2026-08-12**, reports **Deno 2.9.5 / V8 15.0.245.2 / macOS arm64** accepting `import defer` in `deno run` and producing an executable with plain `deno compile`, but failing `deno compile --bundle` and `Deno.bundle()` with `Expected "from" but found "*"`. The reporter found downloaded **esbuild 0.25.5**. The issue is open in the scrape and its comments endpoint returned no comments. This is a community reproduction, not a maintainer certification or a local 2.9.6 measurement. **Confidence: medium-high as a concrete adjacent-version report.** [Deno #36560](https://github.com/denoland/deno/issues/36560).

- **Important correction to that report's proposed fix:** Its suggestion that an esbuild upgrade alone may solve bundling is not established. esbuild **0.25.7**'s changelog says it added **syntax support only**: “These imports cannot currently be bundled by esbuild”; the imported paths must be external and output must be `esm`. Wallace's **2025-07-18** #4238 comment promises syntax support and discusses proxy/escape-analysis complexity for actual bundling. The issue being closed does not itself prove deferred modules can be bundled. **Confidence: high for the 0.25.7 limitation; subsequent-release behavior unverified.** [esbuild 0.25.7 changelog](https://github.com/evanw/esbuild/blob/main/CHANGELOG-2025.md#0257); [maintainer comment](https://github.com/evanw/esbuild/issues/4238#issuecomment-3090281673); [Deno report's suggestion](https://github.com/denoland/deno/issues/36560).

- **Bundle versus compile is a real pipeline distinction:** Live Deno docs identify `deno bundle` as esbuild-powered. Live compile docs now describe experimental `deno compile --bundle` as esbuild bundling before embedding, distinct from default compilation's embedding behavior. Their broad statement that pure-ESM tree-shaking removes “everything unused” needs the narrower esbuild namespace/effect qualifications above. **Confidence: high for the documented distinction, not a promise of perfect elimination.** [Deno bundle docs](https://docs.deno.com/runtime/reference/cli/bundle/); [Deno compile bundling docs](https://docs.deno.com/runtime/reference/cli/compile/#bundling-dependencies); [esbuild namespace limitation](https://github.com/evanw/esbuild/issues/1420#issuecomment-873786196).

### Inferences

- **There is a credible route to the exact dotted expression with lazy modules, but not through an unchanged eager default-object graph:** a namespace-oriented facade can hold/reexport deferred namespace bindings without touching their properties. Reading `Protocol.Message.User` would initialize the touched module and its required eager dependencies. Untouched sibling modules could remain unevaluated only if the graph has deferred boundaries at the relevant levels and no other eager path reaches them. This is a design possibility supported by semantics, **not an implementation validated here**. **Confidence: medium-high.** [Deferred namespace reexports](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#exporting_a_deferred_namespace); [module-level evaluation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#description); [Deno 2.8 support](https://deno.com/blog/v2.8#import-defer).

- **Default-object shape matters even for `import defer`:** deferring a module that default-exports an object gives a namespace with a `default` property, not the default object itself. Accessing `.default` to construct the current aggregate triggers that module's evaluation. Deferring only the root postpones the whole eager graph until first use; it does not leave sibling schema initializers asleep after `User` is accessed. Preserving the exact public shape would require deliberate facade/export or getter/factory design, for the owner to assess. **Confidence: high as semantic inference.** [Deferred namespace default property and triggers](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#deferred_module_namespace_object); [module-granular evaluation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#description).

- **Dynamic `import()` is another boundary, with an async trade-off:** the caller can await an optional subsystem and then use normal synchronous dot notation within it, but `import()` cannot transparently return a schema synchronously on a first property read. Native `import defer` is specifically relevant because it avoids that async boundary while deferring only evaluation. **Confidence: high.** [Dynamic import return value](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#return_value); [import defer versus import()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#description).

- **Use separate success criteria:** (1) bytes/modules excluded from the executable, (2) modules embedded but unevaluated, (3) schema objects constructed, (4) startup time, and (5) process memory. Deferral addresses evaluation and possibly downstream allocations; it does not imply byte removal, avoided linking, or a quantified RSS reduction. **Confidence: high for the distinction; performance remains unknown.** [Deno embedded dynamic imports](https://docs.deno.com/runtime/reference/cli/compile/#dynamic-imports); [defer's eager loading/linking](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#description).

### Gaps

- Actual compiled-executable startup, initialization counts, memory use, and binary size remain **unmeasured**, as stated in the assignment. No additional experiments were performed.
- Deno 2.8 documents runtime support, and the 2.9.5 report documents plain compilation producing an executable. We have not independently verified deferred evaluation inside the project's **2.9.6** executable, its bundling mode, target platform, or its exact pinned esbuild version.
- esbuild 0.25.7 only supported the syntax with imports external to the bundle. Whether later versions implement full deferred bundling, and whether Deno 2.9.6 picks them up, remains unverified. Do not report “upgrade esbuild and it works” from the Deno reporter's hypothesis.
- The repository uses **tsgo** and house lint; acceptance of `import defer`, inferred namespace/default shapes, and any lint-policy implications would need a separate owner-approved evaluation. Runtime support does not establish workspace-tool support.
- Deferred per-member initialization would require auditing dependency cycles, top-level await, eager alternative imports, schema references, and namespace inspection. None were examined or changed here.

## 3. What can `sideEffects`, purity annotations, and other bundlers actually change?

### Takeaway

**`sideEffects: false` permits omission of an otherwise unused module; a pure-call annotation permits omission of a particular unused call. Neither makes a referenced namespace member unused, and neither creates runtime laziness.** Zod's top-level builders introduce a second retention problem, but asserting global purity is not justified: registry registration and other observable initialization require explicit consideration. [esbuild annotation distinction](https://esbuild.github.io/api/#ignore-annotations); [pure-call semantics](https://esbuild.github.io/api/#pure); [Zod registries](https://zod.dev/metadata#registries).

### Cited Findings

- **Granularity:** esbuild defines tree-shaking as “declaration-level dead code removal.” Its `sideEffects` documentation says a file can be removed “if all imports from that file end up being unused.” It does not describe the field as marking every function call inside a partly used module pure, or as permission to delete referenced object properties. **Confidence: high.** [Tree-shaking definition, live](https://esbuild.github.io/api/#tree-shaking); [sideEffects docs, live](https://esbuild.github.io/api/#ignore-annotations).

- **`/* @__PURE__ */` / `/* #__PURE__ */` applies to a call or `new` expression:** esbuild explains that “pure” means “ok to be removed if unused,” not referential transparency, permission to cache results, or a function-wide guarantee. Side-effectful arguments remain evaluated even when the annotated outer call disappears. Its docs demonstrate an annotated IIFE as a way to make an entire initialization body removable when its result is unused. **Confidence: high.** [Pure semantics, live](https://esbuild.github.io/api/#pure); [IIFE example](https://esbuild.github.io/api/#tree-shaking-and-side-effects).

- **Why conservative retention is expected:** esbuild explains that member reads may invoke getters, string coercion may invoke user code, and even a global identifier can throw. Wrong developer annotations can break behavior. **Confidence: high.** [Side-effect analysis, live](https://esbuild.github.io/api/#tree-shaking-and-side-effects); [annotation accuracy](https://esbuild.github.io/api/#ignore-annotations).

- **Direct historical Zod user report:** On **2022-08-26**, a user testing **esbuild 0.15.5** reported shared module-level Zod validators all being retained unless call-site annotations were added; on **2023-03-20**, another user raised generated `ts-to-zod` code as the same problem. These are corroborating community reports, not current Zod-maintainer guarantees. **Confidence: medium-high for historical symptom; version-specific.** [Zod report in #1883](https://github.com/evanw/esbuild/issues/1883#issuecomment-1228591630); [generated schemas follow-up](https://github.com/evanw/esbuild/issues/1883#issuecomment-1475465475).

- **Do not misread function annotations:** In **2021-12-23**, Wallace rejected changing `__PURE__` to mean function-wide purity because other tools use it at call sites. Rollup later added the distinct `__NO_SIDE_EFFECTS__` annotation. In **2023-06-09**, Wallace said esbuild could preserve it, but its effect analysis was local to each file, preventing implementation with its then-current tree-shaking code. The later esbuild discussion is about preserving placement, not a claim to implement Rollup's semantics. **Confidence: high for the dated statements.** [#1883 maintainer](https://github.com/evanw/esbuild/issues/1883#issuecomment-1000554248); [#3149 maintainer](https://github.com/evanw/esbuild/issues/3149#issuecomment-1584954956); [preservation follow-up](https://github.com/evanw/esbuild/issues/3149#issuecomment-1585820844).

- **Current Rollup docs document different capabilities and responsibilities:** `__NO_SIDE_EFFECTS__` marks a function declaration so calls can be treated as effect-free; `manualPureFunctions` is a name-based assertion with propagation to properties/returned functions. Rollup core does **not** itself read package `sideEffects`; its node-resolve plugin can translate the field into per-module flags. Therefore a direct-source Rollup probe's configuration matters. **Confidence: high.** [Rollup declaration annotation](https://rollupjs.org/configuration-options/#no-side-effects); [manual purity](https://rollupjs.org/configuration-options/#treeshake-manualpurefunctions); [module side effects](https://rollupjs.org/configuration-options/#treeshake-modulesideeffects).

- **Zod's own documentation supports a qualified API-design conclusion:** Zod Mini uses top-level functions instead of many methods because bundlers generally cannot remove unused method implementations but can remove unused top-level functions. The author also says regular Zod is generally preferable absent unusually strict size constraints and explicitly recommends user-specific benchmarks. This concerns library implementation size, not proof that every unused application schema initializer is removed. **Confidence: high for the documented distinction; no project-specific size or startup inference.** [Zod Mini tree-shaking](https://zod.dev/packages/mini#tree-shaking); [Zod Mini trade-offs](https://zod.dev/packages/mini#when-not-to-use-zod-mini).

- **Concrete reason not to label all Zod chains pure:** Zod documents `.register()` adding a schema to a registry, `.meta()` registering metadata in `z.globalRegistry`, and duplicate registered IDs throwing. Those observable behaviors defeat a blanket assumption that any call with a `z`-related name can simply disappear. **Confidence: high for documented API behavior.** [Zod registries and register](https://zod.dev/metadata#registries); [global registry](https://zod.dev/metadata#zglobalregistry); [meta](https://zod.dev/metadata#meta).

### Inferences

- **For an unused schema in its own removable module**, truthful module-side-effect metadata can permit dropping the whole module, including its top-level construction. **For an unused schema alongside a used schema in the same retained module**, call-level analysis or annotations may still be needed. **For a schema still referenced by a live `Message` object**, neither annotation solves the reference-retention problem by itself. **Confidence: high.** [Module-level rule](https://esbuild.github.io/api/#ignore-annotations); [call-level rule](https://esbuild.github.io/api/#pure); [object-property problem](https://github.com/evanw/esbuild/issues/2855).

- **One annotation on `z.object({ field: z.string() })` is not automatically an annotation on `z.string()`:** the nested call is an argument computation. Fluent chains similarly require examining which receiver and argument expressions remain when a final call is dropped. A carefully audited initialization boundary can be more meaningful than mechanically asserting every call pure, but no such rewrite is selected here. **Confidence: high for argument evaluation; specific chain output unverified.** [esbuild argument retention](https://esbuild.github.io/api/#pure); [annotated initialization IIFE](https://esbuild.github.io/api/#tree-shaking-and-side-effects).

- **The minimal decision framework is to identify the target first:** byte pruning needs usable module/export reachability plus safe elimination of initializers; delayed initialization needs evaluation boundaries; stable public spelling is a separate constraint that can be retained under some designs. Rollup, Zod Mini, purity metadata, source transforms, and native deferred imports address different portions of that problem. No single one is adopted by this research. **Confidence: high.** [esbuild reachability](https://esbuild.github.io/api/#tree-shaking); [annotations](https://esbuild.github.io/api/#ignore-annotations); [deferred evaluation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer#description); [Zod Mini](https://zod.dev/packages/mini#tree-shaking).

### Gaps

- The assignment reports **two real schema probes retaining unused initialization in Deno bundles**; this research did not inspect or rerun them. It does not establish which individual constructors, nested calls, registry writes, or aggregate references caused retention.
- The project's Zod version and schema-construction patterns were not audited for purity. Zod 4 documentation is relevant evidence against a blanket rule, not proof that this code currently uses those registry APIs.
- Deno's exact handling of package `sideEffects` through its resolver, and which esbuild purity controls its bundling CLI exposes in 2.9.6, were not verified. Generic esbuild options are not automatically available as `deno bundle` flags.
- No universal bundle-size, initialization-count, startup-time, or memory benefit can be estimated from the sourced toy examples or the supplied probes. A future owner-approved comparison would need the real application entry point, exact tool versions, evaluation counts, and compiled measurements; this task performs research only.
