# Readable namespace APIs, startup graphs, and memory: community patterns

Part of [[features/engine-foundation/research/deno-namespace-bundling]].

Research date: **2026-10-06**. Scope: a Deno-first application distributed as one `deno compile` executable, retaining the readability of `Protocol.Message.User`. Research and planning only; no application implementation, dependency changes, or experiments were performed.

All web discovery and retrieval used the installed **Firecrawl CLI**, through both `firecrawl search` and `firecrawl scrape`. Raw search JSON and captured Markdown text are in `sources/patterns/`. Sources below distinguish **high confidence** primary documentation, **medium confidence** project-specific reports, and **low confidence** unverified issue assertions. Confidence concerns the cited claim, not its transfer to this application. Moving documentation was retrieved on the research date; historical examples are explicitly bounded.

## 1. What do established projects actually preserve: flat namespaces or nested objects?

### Takeaway

The strongest documented precedent is **named ESM exports accessed through a flat module namespace**, such as `Schema.foo`, sometimes imported from a section subpath. That is materially different from an ordinary default-exported object containing other objects; even nested ESM namespace re-exports have bundler-dependent limitations. [esbuild namespace transformation](https://esbuild.github.io/content-types/#module-namespace-this), [Effect import guidance](https://effect.website/docs/v3/micro/effect-users#importing-micro), [esbuild nested-namespace report](https://github.com/evanw/esbuild/issues/2636).

### Cited Findings

- **Effect, v3 documentation — high confidence, with a bundler qualification.** Its Micro guide shows both `import { Micro } from "effect"` and `import * as Micro from "effect/Micro"`; both preserve `Micro.foo`. It cautions: “Named imports may generate tree shaking issues when a bundler doesn’t support deep scope analysis.” Here, “named imports” means the root import of a **module namespace**, not a general objection to named leaf exports. The guide lists Rolldown, Rollup, and Webpack 5+ as supporting the requisite analysis. This is direct evidence for section-level namespace imports, not proof that arbitrary `Effect.Section.foo` or default-object trees optimize equally. [Effect](https://effect.website/docs/v3/micro/effect-users#importing-micro).
- **Zod Mini, v4-era documentation — high confidence.** The documented API is `import * as z from "zod/mini"` followed by functions such as `z.optional(z.string())`. Its explanation explicitly contrasts top-level functions, which bundlers can remove individually, with unused instance methods, which generally cannot be removed. It retains a flat `z.foo` namespace but trades away much of regular Zod’s chaining. The maintainer calls Mini “more verbose and less discoverable” and prefers regular Zod’s ergonomics. This is an API-design tradeoff, not a recommendation to replace this application’s schema library. [Zod Mini](https://zod.dev/packages/mini?id=tree-shaking).
- **Zod nested namespaces — medium/low confidence caution, not a general theorem.** Issue #6050, opened 2026-06-02, reports all locales being retained behind `export * as locales`; it was closed when retrieved. The scraped page does not expose a maintainer explanation or resolution, so its claimed webpack/Rollup behavior is an issue author’s report, not established current behavior. It illustrates why `z.foo` success does not settle `z.locales.foo`. [Zod #6050](https://github.com/colinhacks/zod/issues/6050).
- **lodash-es — medium confidence practitioner evidence.** Pedro Figueiredo’s November 2023 writeup recommends `import * as _ from "lodash-es"` and static `_.method()` calls instead of the default import of an object containing all utilities. This agrees with esbuild’s documented namespace lowering. A contrary August 2025 Honeybee issue claims namespace imports prevent effective tree shaking and proposes named imports, but provides no reproducible bundler configuration or measurement in the retrieved body. The evidence supports testing the exact pipeline, not declaring namespace imports universally good or bad. [Practitioner writeup](https://dev.to/pffigueiredo/making-lodash-tree-shakable-3h27), [contrary project issue](https://github.com/coscene-io/honeybee/issues/1019), [esbuild](https://esbuild.github.io/content-types/#module-namespace-this).
- **RxJS — high confidence, explicitly versioned.** The official importing guide says v7.2.0 moved most operators to the root `rxjs` export site and prefers it over `rxjs/operators`. It documents both named imports and `import * as rxjs from "rxjs"`, used as `rxjs.of(...).pipe(rxjs.map(...))`; specialized subpaths include `rxjs/ajax`, `rxjs/fetch`, `rxjs/webSocket`, and `rxjs/testing`. Its older nested `rxjs.operators` example is for a globally imported bundle, not evidence of tree-shakable nested ESM. RxJS therefore contradicts a blanket “every library recommends leaf subpaths” claim. The rendered site scrape was empty, so the evidence is its official documentation source. [RxJS guide source](https://github.com/ReactiveX/rxjs/blob/master/apps/rxjs.dev/content/guide/importing.md).
- **esbuild — high confidence mechanism; historical nested-case limit.** Its docs explain that namespace member calls are normally rewritten to direct imports, enabling dead-export removal; they also document a `this`-binding caveat. Its tree shaking is described as “declaration-level dead code removal.” Jake Bailey’s October 2022 TypeScript-compiler report shows nested namespace re-exports emitting an exports object where direct section imports emit a direct call; the issue remained open when retrieved. That example establishes an optimization limitation, not an independently measured startup or RAM regression. [Namespace transformation](https://esbuild.github.io/content-types/#module-namespace-this), [tree shaking](https://esbuild.github.io/api/#tree-shaking), [#2636](https://github.com/evanw/esbuild/issues/2636).

### Inferences

- Three source shapes need separate treatment: **(a)** `import * as Message from ".../message"; Message.User`, **(b)** ESM namespace re-exports accessed as `Protocol.Message.User`, and **(c)** the current, user-described default-object tree accessed identically. The common dotted spelling does not make their optimization opportunities equivalent. Changing (c) to (b) could preserve call-site spelling, but the retrieved evidence does not justify promising leaf-level shaking in Deno’s esbuild pipeline. [esbuild docs](https://esbuild.github.io/content-types/#module-namespace-this), [nested case](https://github.com/evanw/esbuild/issues/2636).
- A plain default object is not inherently forbidden or always unoptimizable. The bounded conclusion is that object-property elimination needs analysis beyond simply discarding unused ESM export declarations; do not treat namespace-import success as a guarantee for that object. [esbuild’s declared optimization scope](https://esbuild.github.io/api/#tree-shaking).

### Gaps

- No retrieved source proves an unmodified, arbitrary-depth default-object API tree is optimally eliminated by the exact Deno/esbuild versions used here.
- These library import examples do not quantify this application’s startup time or memory. The installed library versions and schema initialization behavior were not investigated as part of this community-research assignment.

## 2. What do subpaths and section imports cost aesthetically?

### Takeaway

Section imports are an established middle ground: preserve a recognizable dotted section API while narrowing the import boundary. They usually move part of the hierarchy from the expression into the import path; the root-prefix loss is a real aesthetic compromise, not an implementation detail. [Effect](https://effect.website/docs/v3/micro/effect-users#importing-micro), [RxJS](https://github.com/ReactiveX/rxjs/blob/master/apps/rxjs.dev/content/guide/importing.md).

### Cited Findings

- **Atlassian/Jira, 2025-06-26 — medium/high confidence for its own tooling.** Its engineering writeup describes removing cascading barrels with a graph-aware codemod and ESLint enforcement. The reported gains concern build, test, and editor workloads; the article reports only a slight bundle-size drop in its initial evaluation. It acknowledges reduced public-API encapsulation, more fragile file moves, and potential coupling through deep imports. Its headline performance percentage is not a Deno executable startup measurement. [Atlassian](https://www.atlassian.com/blog/how-we-build/faster-builds-when-removing-barrel-files).
- **MSW discussion, January–February 2024 — medium confidence, useful disagreement.** Contributors propose granular/grouped entrypoints while retaining the root for compatibility and avoiding internal imports through that root. Maintainer discussion raises API maintenance, duplicated type/runtime identity, and the possibility of encountering another barrel deeper in the graph. It also asks for actual load-time measurements rather than download-size proxies. The thread distinguishes unbundled test/dev workloads from production bundling; there is no universal consensus that all barrels must go. [MSW #2037](https://github.com/mswjs/msw/discussions/2037).
- **Subpaths coexist with ergonomic roots in actual libraries.** Effect offers the root namespace import and direct module import; RxJS retains specialized section entrypoints while moving most operators toward the root in v7.2.0. The common pattern is deliberate public import boundaries, not necessarily exposing private implementation files. [Effect](https://effect.website/docs/v3/micro/effect-users#importing-micro), [RxJS](https://github.com/ReactiveX/rxjs/blob/master/apps/rxjs.dev/content/guide/importing.md).

### Inferences

- An illustrative public section import such as `import * as Message from "@app/protocol/message"` keeps `Message.User` readable and synchronous, but removes the literal `Protocol.` qualifier. An alias such as `ProtocolMessage.User` restores provenance at the cost of changing the visual hierarchy. These are options for the user to judge, not a selected naming scheme. [Section-import precedent](https://effect.website/docs/v3/micro/effect-users#importing-micro).
- Stable public subpaths could conceal implementation-file moves better than arbitrary deep imports. Keeping a compatibility root would preserve discoverability, but any startup-sensitive consumer still using that root would need its own graph examined. A section’s transitive imports must actually avoid reaching back into the full root. [MSW discussion](https://github.com/mswjs/msw/discussions/2037), [Atlassian tradeoffs](https://www.atlassian.com/blog/how-we-build/faster-builds-when-removing-barrel-files).
- A smaller source import graph can help build-time graph traversal even when final tree-shaken output barely changes. Conversely, a bundled executable may already eliminate a barrel that hurts unbundled development. These are separate measurements. [Vercel explanation](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js), [Atlassian observations](https://www.atlassian.com/blog/how-we-build/faster-builds-when-removing-barrel-files).

### Gaps

- The user has not chosen whether losing the outer `Protocol.` qualifier is acceptable. No naming or export-surface decision is made here.
- Community reports do not establish which sections would constitute useful boundaries in this application, or how much shared schema machinery remains reachable from each.

## 3. Can build-time transforms preserve the exact dotted source API?

### Takeaway

Yes, there is a concrete precedent for keeping dotted calls in source while emitting leaf imports: Lodash’s Babel plugin. However, Next’s barrel optimizers and generic import plugins do not by themselves establish support for arbitrary `Protocol.Message.User` chains; extending that idea to this API would be explicit build-tool work. [Lodash plugin](https://github.com/lodash/babel-plugin-lodash), [Next documentation](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports), [generic plugin limitations](https://github.com/avocadowastaken/babel-plugin-direct-import#limitations).

### Cited Findings

- **Next.js, maintainer explanation dated 2023-10-13 — high confidence for its mechanism.** `modularizeImports` uses a configured member-to-path mapping, e.g. rewrites `import { module2 } from "my-lib"` to its leaf import. `optimizePackageImports`, introduced in Next 13.5, discovers mappings from barrels, recursively handles nested barrels and `export *`, and stops when reaching a non-barrel file. “Nested barrels” here means re-export chains; it is not a promise to rewrite arbitrary nested runtime property access. The article distinguishes eliminating runtime loading of externalized packages from saving graph traversal during bundling. [Vercel](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js).
- **Current Next documentation — high confidence, moving page.** The retrieved page, last updated 2025-12-19, describes convenience for “import statements with many named exports” and still labels `experimental.optimizePackageImports` experimental. This is a Next compiler/configuration feature, not a Deno CLI option. [Next docs](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports).
- **`babel-plugin-lodash` — high confidence historical precedent.** Its README demonstrates `import _ from "lodash"; _.map(...)` being transformed to an import from `lodash/map` and a direct `_map(...)` call. It explicitly does not support chain sequences and requires ES2015 imports. The repository was archived on 2023-09-16: useful proof of the approach, not evidence of a currently maintained universal optimizer. [Plugin README](https://github.com/lodash/babel-plugin-lodash).
- **Generic plugins vary — high confidence about this plugin’s own limitations.** `babel-plugin-direct-import` explicitly says, “Namespace imports are hard to analyze, that’s why we skip them.” It also documents problems with variable-export mappings. Merely choosing an import-optimization plugin does not guarantee dotted-access rewriting. [Plugin limitations](https://github.com/avocadowastaken/babel-plugin-direct-import#limitations).
- **Deno applicability — high confidence about existing bundling, not custom transforms.** Current Deno docs describe `deno bundle` as esbuild-based and `deno compile --bundle` as an experimental esbuild preprocessing path. The Deno 2.9 release announcement dated 2026-06-25 documents the new compile flag. None of these retrieved docs describes a Next-style configurable nested-member import transform. [Deno bundle](https://docs.deno.com/runtime/reference/cli/bundle/), [Deno compile](https://docs.deno.com/runtime/reference/cli/compile/#bundling-dependencies), [Deno 2.9](https://deno.com/blog/v2.9#deno-compile).

### Inferences

- **Plausible design, not an implemented capability:** a binding-aware AST pass could recognize a known `Protocol` import and rewrite static `Protocol.Message.User` reads to a private local binding imported from the corresponding leaf module, leaving authored source readable. It would need an explicit or derived export map and would have to remove the root import only when all relevant references and side effects are accounted for. This generalizes the Lodash precedent beyond what its README promises. [Lodash transformation](https://github.com/lodash/babel-plugin-lodash), [Next mapping model](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js).
- **The difficult cases are semantic, not just syntax matching:** computed keys whose values are not known statically; namespace escape via passing/storing/spreading/enumerating it; aliases and destructuring; mutation; getters/proxies; `this`-sensitive method calls; initialization order and side effects; cycles; and TypeScript type-only versus runtime use. Each needs supported semantics, conservative fallback, or an explicit unsupported-case diagnostic. Regex replacement would not establish equivalence. This is an engineering inference from documented namespace-call and side-effect constraints, not a claim that every existing optimizer fails every case. [esbuild namespace caveat](https://esbuild.github.io/content-types/#module-namespace-this), [side-effect analysis](https://esbuild.github.io/api/#tree-shaking), [plugin limitations](https://github.com/avocadowastaken/babel-plugin-direct-import#limitations).
- **Deno-first integration work would include** a pre-compilation transformation stage, resolver/export-map handling for the workspace, source maps and diagnostics, semantic parity with untransformed dev/test runs, and a way to inspect fallback references that still retain the root. The output could still be compiled into one executable; using this precedent does not imply adopting Next, Babel, or another runtime. These are candidate requirements, not selected tooling. [Deno bundling entrypoint](https://docs.deno.com/runtime/reference/cli/compile/#bundling-dependencies), [Lodash precedent](https://github.com/lodash/babel-plugin-lodash).

### Gaps

- No retrieved maintained tool demonstrably handles this exact arbitrary-depth default-object API in a Deno-first pipeline without custom mapping or logic.
- No transform compatibility, development/build parity, or benefit was tested. A full native Deno plugin-extension survey was outside scope; absence from the retrieved docs is not proof that no extension route exists.

## 4. What do getters, factories, and dynamic imports actually defer?

### Takeaway

A synchronous getter or factory can defer **schema construction** if construction is moved inside it; a getter returning an already-created statically imported schema does not defer that module’s evaluation. Dynamic `import()` introduces an asynchronous loading boundary and module caching, not automatic unloading. [MDN import](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import), [MDN getters](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/get#smart_self-overwriting_lazy_getters).

### Cited Findings

- **Static versus dynamic import — high confidence language documentation.** MDN states that ordinary static imports evaluate imported modules at load time, whereas `import()` evaluates on demand and returns a Promise fulfilled after loading/evaluation. A dynamic import of an embedded module is still asynchronous; “already available in the executable” does not make its return value a synchronous schema. [MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import).
- **Lazy getters — high confidence mechanism.** MDN distinguishes calculating a value on property access from memoization: an ordinary getter is not automatically cached. A smart getter computes on first access and caches its result for subsequent accesses. This defers the calculation inside the getter, not the evaluation of modules imported by its enclosing module. The latter conclusion follows from ordinary import semantics. [Getter documentation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/get#smart_self-overwriting_lazy_getters), [import semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import).
- **Concrete memory-focused precedent: Zod 4.5 — high confidence about the maintainer’s reported benchmark, not an application forecast.** Colin McDonnell’s 2026-08-26 post describes replacing eagerly allocated bound methods with prototype getters that bind a method on first access and install it as an own property. It reports retained heap for `z.string()` falling from 7.53 kB in 4.4.3 to 784 bytes in 4.5 and links its benchmark. This preserves convenient methods while delaying their allocations. It is evidence for object-allocation laziness, not deferred module loading or this application’s RSS. [Zod memory post](https://zod.dev/blog/reducing-memory-footprint).
- **Module caching — high confidence.** MDN says modules execute at most once per module identity and there is no API to clear the module namespace cache. It specifically warns that varying URL query parameters to re-import can leak memory. Finishing a feature’s operation does not automatically unload its imported module. This does not imply that every temporary object allocated by that module is permanently retained. [MDN cache discussion](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object).
- **Single executable is compatible with runtime deferral — high confidence inclusion rules.** Deno compile includes literal dynamic imports in the binary; computed specifiers may require explicit `--include`. Thus deployment can remain one executable while activation is delayed. Current experimental `--bundle` has additional static-analysis limits for dynamic patterns; their details need version-specific verification. [Deno dynamic imports](https://docs.deno.com/runtime/reference/cli/compile/#dynamic-imports), [bundle limitations](https://docs.deno.com/runtime/reference/cli/compile/#limitations).
- **Bundling can preserve async semantics without separate chunks — high confidence esbuild documentation.** With code splitting disabled, esbuild documents lowering `import()` to `Promise.resolve().then(() => require())`, retaining the imported code in the same bundle. This distinguishes deferred execution from deferred inclusion or separate-file loading; it does not establish how many bytes V8 parses, compiles, or retains at each stage of a Deno executable. [esbuild splitting](https://esbuild.github.io/api/#splitting).
- **Emerging separate mechanism, support unresolved here:** MDN’s `import defer` page, updated 2026-09-22, describes synchronous evaluation on namespace-property access after up-front fetching/linking; top-level-await modules are eagerly evaluated. It is explicitly a limited-availability feature. Do not confuse it with an ordinary getter, and do not claim all synchronous module deferral is impossible. This research did not verify Deno, its embedded V8, esbuild, or `deno compile` support for it. [MDN import defer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer).

### Inferences

- To preserve synchronous `Protocol.Message.User`, a memoized getter could construct `User` from already-available primitives when first accessed. A getter that merely returns the imported `User` singleton changes access mechanics but not eager schema construction. A factory such as `getUserSchema()` offers similar construction deferral with an explicit call-site change. [MDN getters](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/get#smart_self-overwriting_lazy_getters), [static imports](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import).
- Memoization trades repeated construction for retained cached state after use. To defer module evaluation with ordinary dynamic imports while keeping feature-internal schema reads synchronous, an asynchronous feature loader could await the feature module before calling its synchronous logic. An uninitialized synchronous getter cannot synchronously return the eventual result of `import()`. [MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import).
- Initial and eventual memory can differ: unused constructions might never occur, while a long-lived process exercising every feature may eventually populate every cache. Getter-based APIs can also complicate dead-code analysis because property reads may have side effects. Neither direction is a measured result for this application. [Getter caching](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/get#smart_self-overwriting_lazy_getters), [module cache](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object), [esbuild side-effect analysis](https://esbuild.github.io/api/#tree-shaking).

### Gaps

- No measurement identifies whether this application’s dominant cost is schema construction, module evaluation, parsing/compilation, native runtime baseline, or other retained state.
- First-use latency, recursive-schema initialization, singleton identity requirements, concurrent loading/error policy, and post-use heap retention remain application-specific.
- The Deno docs claim runtime-memory benefits for `--minify`, but do not provide a measurement applicable here. This note does not convert code-size reductions, compressed bundle sizes, or executable-size reductions into RAM estimates. [Deno minification docs](https://docs.deno.com/runtime/reference/cli/compile/#minifying-the-bundle).

## 5. What neutral options and next-step plan follow from the evidence?

### Takeaway

There are three distinct optimization targets: removing unreachable code at build time, delaying evaluation until a feature activates, and avoiding allocations until values are used. The user can retain the exact dotted spelling through some candidates, but the evidence does not select a winner or establish a speed/RAM improvement for any candidate. [esbuild tree shaking](https://esbuild.github.io/api/#tree-shaking), [dynamic imports](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import), [Zod allocation example](https://zod.dev/blog/reducing-memory-footprint).

### Cited Findings

- As of the retrieved Deno 2.9 announcement and current docs, bundling before compilation can be requested using experimental `deno compile --bundle`; plain compilation and bundled compilation are therefore separate configurations. One executable does not, by itself, specify a tree-shaking strategy. The exact local Deno version and intended production flags must be identified before transferring any esbuild result. [Deno 2.9](https://deno.com/blog/v2.9#deno-compile), [compile reference](https://docs.deno.com/runtime/reference/cli/compile/#bundling-dependencies).
- Maintainer and practitioner sources demonstrate different benefits: Effect documents namespace import compatibility; Atlassian reports tooling graph improvements; Vercel reports Next-specific import optimization; Zod reports retained heap per schema instance. They measure or discuss different systems and quantities, so their percentages are not interchangeable estimates for this executable. [Effect](https://effect.website/docs/v3/micro/effect-users#importing-micro), [Atlassian](https://www.atlassian.com/blog/how-we-build/faster-builds-when-removing-barrel-files), [Vercel](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js), [Zod](https://zod.dev/blog/reducing-memory-footprint).

### Inferences

The following comparison is a research-derived planning aid, **not an adopted design**:

| Candidate | Source/readability impact | Intended target | Deno fit and unresolved point |
| --- | --- | --- | --- |
| Current nested objects, with explicit production bundling | Exact `Protocol.Message.User` retained | Establish what existing DCE can remove | Low API disruption; member-level elimination and eager schema construction remain unproven. [esbuild](https://esbuild.github.io/api/#tree-shaking) |
| Flat section namespace imports | `Message.User` or an explicit section alias | Narrow source graph; expose named-export DCE | Native ESM pattern; transitive graph may still be broad. Outer prefix changes. [Effect](https://effect.website/docs/v3/micro/effect-users#importing-micro) |
| Nested ESM namespace re-exports | Potentially exact dotted call sites, with different export representation | Better static visibility than ordinary objects | Requires checking the selected bundler’s nested-namespace behavior; historical esbuild limitation exists. [#2636](https://github.com/evanw/esbuild/issues/2636) |
| Build-time dotted-access lowering | Exact authored spelling for supported static accesses | Emit leaf imports without authoring them everywhere | Custom mapping/analysis/integration and semantic fallback policy; established flat Lodash precedent, no proven turnkey Deno solution. [Lodash plugin](https://github.com/lodash/babel-plugin-lodash) |
| Memoized synchronous schema getters/factories | Getter can retain exact spelling; factory adds a call | Delay schema or method allocations | Does not defer static imports; caches retain first-use results; possible getter/DCE interaction. [MDN getter](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/get#smart_self-overwriting_lazy_getters), [Zod example](https://zod.dev/blog/reducing-memory-footprint) |
| Dynamic feature imports | Async activation boundary; synchronous API after activation | Delay evaluation of feature subgraphs | Literal imports can be embedded in one binary; cached modules are not automatically unloaded; first-use cost and memory remain unknown. [Deno](https://docs.deno.com/runtime/reference/cli/compile/#dynamic-imports), [MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import) |

Proposed sequence for a later, separately authorized evaluation:

1. **Record the actual production pipeline**: Deno version, whether compilation bundles, minification, external/CJS dependencies, and the role of literal versus computed dynamic imports. Keep build graph, embedded code, evaluated startup graph, and live allocations separate. [Deno compile](https://docs.deno.com/runtime/reference/cli/compile/#bundling-dependencies), [esbuild splitting](https://esbuild.github.io/api/#splitting).
2. **Ask the owner which API properties are essential**: exact three-level spelling, synchronous first access, ability to pass/reflect over `Protocol`, singleton schema identity, or chiefly readability. This determines whether section imports, lowering, or deferred construction are acceptable candidates. The question is motivated by the actual syntax and semantic compromises above. [Effect alternatives](https://effect.website/docs/v3/micro/effect-users#importing-micro), [namespace-call caveat](https://esbuild.github.io/content-types/#module-namespace-this), [getter semantics](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Functions/get#smart_self-overwriting_lazy_getters).
3. **Only after authorization, compare a small representative boundary** across the owner-approved candidates. Inspect emitted reachable code and eager initializers; measure process-to-ready latency, first-use latency, startup/after-use RSS, and retained JS heap separately. Include an always-used schema and an optional feature; do not infer performance from compressed size alone. This is a proposed measurement plan, not executed research. [MSW demand for load-time evidence](https://github.com/mswjs/msw/discussions/2037), [Zod retained-heap methodology](https://zod.dev/blog/reducing-memory-footprint), [Atlassian graph/output distinction](https://www.atlassian.com/blog/how-we-build/faster-builds-when-removing-barrel-files).
4. **If considering a transform, settle its supported language subset before implementation** and verify equivalent behavior for aliases, escaping namespaces, side effects, cycles, getter access, and type positions. If considering laziness, define first-use and error/caching behavior. Return those tradeoffs and measurements to the owner rather than selecting a design by analogy. [Plugin limitations](https://github.com/avocadowastaken/babel-plugin-direct-import#limitations), [esbuild side-effect constraints](https://esbuild.github.io/api/#tree-shaking), [module cache behavior](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/import#module_namespace_object).

### Gaps

- **No option has been chosen, benchmarked, or implemented.** Current startup and RAM baselines, acceptable first-use delay, and the owner’s exact syntax tolerance remain unknown.
- `import defer` is a watch-list item rather than a Deno-ready option in this comparison because relevant toolchain support was not established. [MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/import/defer).
- Some searches returned no results, and the RxJS rendered page returned only its shell; these retrieval limitations are recorded in [[features/engine-foundation/research/deno-namespace-bundling/retrieval]]. No substantive finding relies only on a search snippet or on an AI-generated issue reply.
