Feature Request: TC39 Stage 3 `import defer`
--------------------------------------------

Proposal repo: [https://github.com/tc39/proposal-defer-import-eval](https://github.com/tc39/proposal-defer-import-eval)

The new import defer syntax is at Stage 3 in the TC39 process and implementations are starting to move forward in [browsers](https://github.com/tc39/proposal-defer-import-eval/issues/59)
 and tools.

This enables new optimizations in code splitting builds that avoid unnecessary code execution.

Example:

```js
import defer * as mod from './mod.js';

export function lazyModUser () {
  mod.foo();
}
```

where `mod` is a "Deferred Module" flavor of Module Namespace, whose accessors (including e.g. reading keys) cause evaluation to run.

Desired support
---------------

At a minimum the syntax should be tolerated. Ideally this should be a fully compliant downlevel as that will benefit users the most. That requires function-wrapping the modules that will be lazily evaluated, i.e. they cannot be inlined (scope-hoisted).

References
----------

*   [`import defer` proposal](https://github.com/tc39/proposal-defer-import-eval)
     is Stage 3
*   [Babel shipped support](https://babeljs.io/blog/2023/09/25/7.23.0)
     - only works with CommonJS output
*   [webpack merged experimental support](https://github.com/webpack/webpack/pull/16567)
     with [some caveats](https://webpack.js.org/configuration/experiments/#experimentsdeferimport)
    
*   [TypeScript 5.9 Beta shipped support](https://devblogs.microsoft.com/typescript/announcing-typescript-5-9-beta/#support-for-import-defer)
     - syntax passthrough, no downleveling
*   [Rollup issue](https://github.com/rollup/rollup/issues/5932)
    
*   [Rolldown issue](https://github.com/rolldown/rolldown/issues/4857)
    
*   [RsPack issue](https://github.com/web-infra-dev/rspack/issues/10608)
